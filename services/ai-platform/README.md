# @ech/ai-platform

The only service in ECH that calls AI models. Features name a **task / tool**, never a model; the service resolves model aliases, egresses through Cloudflare AI Gateway (optional), records every call in its own ledger, and only ever **stages** changes. The domain owner applies them after a human approves.

- Architecture & decisions: `plans/reports/brainstorm-261019-unified-ai-platform-architecture.md` (Rev 2)
- Roadmap: `plans/261019-ai-platform/plan.md`

## Run locally

```bash
cp apps/ai-platform/.env.example apps/ai-platform/.env.local   # fill DB URL, secret, provider key
pnpm dev:ai                                                    # :8300, applies migrations in dev
```

The Postgres user needs its own database (`ai_platform`), never `commerce_core` / `primeweb`. With no provider key, set `AI_MODEL_BALANCED=mock:copilot` (deterministic dev model, refused in production).

prime-web needs `AI_PLATFORM_URL` and the same `AI_PLATFORM_CONTEXT_SECRET`; the mascot then talks to `/api/agent/*` (BFF) → this service.

## Core

- **Providers** (`src/models/providers.ts`): openai, anthropic, google, openrouter, deepseek, `compat-<name>` (any OpenAI-compatible endpoint, e.g. self-hosted SEA-LION), `mock` (dev only). Direct or via Cloudflare AI Gateway (BYOK supported).
- **Aliases → fallback chains** (`AI_MODEL_FAST`, `AI_MODEL_BALANCED`): `anthropic:claude-haiku-5-5, openai:gpt-4.1-mini` (defaults: fast/balanced = Claude Haiku 5.5, quality = Claude Sonnet 5.5, each with an OpenAI fallback; a provider without a key is skipped). prime-web can override the chains and the price table at runtime (`GET /api/internal/ai-config`, Payload; env is the fallback). Outages fall to the next provider; every attempt is ledgered (`src/models/fallback.ts`).
- **DeepSeek** uses the native `@ai-sdk/deepseek` provider (maps `prompt_cache_hit_tokens` to cached input) in non-thinking mode; prices in `src/ledger/price-book.ts` include DeepSeek's peak/off-peak rates.
- **Task engine** (`src/tasks/*`): task contracts live in `@ech/ai-contracts`; the server side adds alias + versioned prompt. Output is schema-validated (`Output.object`). Callers use `createAiClient().runTask(id, input)`.

## Cache-stable prompts

Providers cache identical prompt prefixes (DeepSeek, OpenAI and Gemini implicitly; Anthropic at the `cache_control` breakpoint the engine sets on the system message, see `src/models/prompt-cache.ts`). Keep the prefix byte-identical across requests:

- System instructions + tool definitions are static: no org/user/site names, page titles, block content, merchant text, dates or per-request lists. Those go in the user turn, after any history (the copilot prefixes a `Context:` line — and a `Selected on the page` line for Ask AI elements — to the merchant's message).
- Instructions may depend only on low-cardinality inputs (locale, language, tone preset, format enum) or tenant/app-stable data (tenant category list, block registry); each variant caches separately. History is append-only; tools stay in a fixed order.
- `src/tasks/catalog/prompt-cache-stability.spec.ts` renders every task for two requests that differ in all other fields and fails unless the instructions are identical; new contract fields must be classified there. Moving text between instructions and prompt bumps `promptVersion`.
- `pnpm --filter @ech/ai-platform usage:report [--days 7] [--org <id>]` prints calls, input / cached tokens, hit ratio and cost per task + provider + model from `ai_usage_events` (read-only).

## Cost controls (copilot)

`tsx scripts/measure-prompt.ts` prints the static prefix (instructions + each tool's schema) per capability set, unrouted and routed.

- **Tool routing** (`AI_TOOL_ROUTING`, default `on`; `src/agent/tool-routing.ts`): a request loads only the tool groups it needs (website, blog, products, inventory, categories, discounts, orders, customers, reports, campaigns, pictures), picked from the chat's user turns (page module and record on each Context line, Ask AI picks, attached files, en / ms / vi keywords of the request, never the Context line's words), its staged lines and the To do task. A group is a capability subset, so a routed request is `merchantInstructions(loaded, full)` + that subset's tools: static bytes per variant (cached separately), and a chat's set only grows, so its history prefix keeps hitting the cache. `use_tools` loads more groups for the next step; a call to an allowed tool that was not sent still runs and loads its group (a middleware filters the tools the provider sees; the SDK keeps the full map). Routing never widens the effective capability set. Full staging set: ≈106 k characters unrouted → 14 k (dashboard / reports), 17 k (orders, discounts, customers), 19 k (blog), 26 k (products), 47 k (website editor). `off` sends everything as before.
- **Tool results** (`src/agent/tool-results.ts`): a read's large part that an earlier read of the same request already returned becomes a pointer; a result over 24 k characters has long texts and lists clipped with a note; `site_read`'s section `version` is dropped. Fresh reads a change is drafted from are never touched.
- **Fewer steps**: `read_item` takes `moreIds` (≤5 records per call) and the instructions ask for batched reads.
- **Read shortcuts** (`src/agent/run-intents.ts`): a message that is exactly one of the platform's read chips ("Show today's sales", en / ms / vi) or a start-run `intent` (`{ tool: "store_reports" | "store_todos", args }`) runs the read and answers from a template with no model call; an error or an unknown shape falls back to the model. Staging tools never shortcut.
- **Suggestions** (`AI_SUGGEST_MODE`, default `rules`): from what the run did (staged cards, reads, the To do list's ready prompts), else one tiny FAST-model call (no tools, no instructions, the last exchange only), and only after a call that hit the cache; `model` skips the rules, `off` makes none.
- **Daily spend guard** (`AI_DAILY_BUDGET_USD`, unset = off; `src/cost/spend-guard.ts`): runs and tasks answer 503 "AI is paused for today, it will be back tomorrow." once the ledger's cost since the Malaysia day's start reaches the budget; one indexed sum per instance a minute (`ai_usage_events_created_cost_idx`), fail-open, warnings at 50 % / 80 %, one error line a minute.

Every request carries a short-lived HS256 context token signed by prime-web (`iss=prime-web`, `aud=ai-platform`, `org`, `sub`, plus `role` = workspace membership role and `name` = display name for "Asked by …"). Draft access between teammates lives in `src/agent/change-set-access.ts` (three rules: chats private; a teammate's drafts only for owners / admins; approve / reject / undo by who asked or an owner / admin, never a viewer — prime-web still checks the change's own permissions when it applies it). Tables: `ai_threads`, `ai_runs`, `ai_change_sets`, `ai_usage_events` (see `src/database/migrations.ts`).

**Capabilities (`AI_AGENT_CAPABILITIES`).** A deployment can offer the copilot less than the full shop. The env value is a comma list; unset = every capability but the opt-in `shop_products` (rewrite/v1's behaviour, byte for byte: tools, schemas and instructions are unchanged). The set decides, in `src/agent/merchant-capabilities.ts` (`TOOL_CAPABILITIES`), which tools the model gets, and also narrows what the rest say: the `kind` of `read_item` / `search_items` / `propose_update` / `propose_status_change`, `find_images` sources, `ask_user` purposes and photo questions, `addToStore` on a page patch, the store rule for drafts made on the `store` page, and the system instructions (one text per set, built once and reused, so the prompt cache keeps hitting; `src/agent/merchant-instructions.ts`). A name that is not in the list, or `store_products` without `product_master`, stops the service at boot.

A request's signed context token may also carry a `caps` claim (array of names, set by the BFF): the request then gets the intersection of the server set and the claim, so it can only narrow. Staging release without platform-api: `AI_AGENT_CAPABILITIES=site,blog,stock_photos` (with the shop's own Payload products: `site,blog,stock_photos,shop_products`); add `store_categories` / `store_discounts` / `store_customers` for the Product Store's categories, the discount codes, and the customers + contact leads + email templates (Payload, no platform-api needed); add `media_library` / `image_generation` when pictures live in that deployment's own media. Tasks (`/v1/tasks`) are not affected.

**Threads + memory.** Each run stores the exact user turn it sent (`ai_runs.user_message`). A run in an existing thread sends: static system prompt + tools, then for each earlier turn (oldest first) that user message and an assistant message with the final answer + one `[Staged draft <id>: <title> — <summary>]` line per staged change set, then the new user turn. Only staging-time data is replayed, so history is byte-stable across turns (prefix cache keeps hitting). Bounded to the newest 20 turns / 24k chars (`src/agent/thread-memory.ts`; summarising dropped turns is a follow-up). **Retention:** threads idle longer than `AI_THREAD_RETENTION_DAYS` (default 90) are hidden at once and swept with their runs + change sets on boot and hourly (`ThreadRetentionService`; on Vercel the timer is off and Vercel Cron calls `/internal/cron/thread-retention` daily); `ai_usage_events` rows stay. The same sweep closes runs a killed process left `planning` / `running` (Vercel stops a function at `maxDuration` without a chance to save): any such run not written for `AI_RUN_MAX_RUNNING_MS` (default 10 min locally, 330 s on Vercel, just above the 300 s function limit) becomes `failed` with "This request was interrupted before it finished. Please try again.", so the chat stops showing it as working. The cron response adds `staleRuns`. The cron is daily and does not run on the staging target, so chat requests (thread list / open, `GET /agent/work`, run start) also start that close in the background (`StaleRunSweeper`, never awaited), at most once per `AI_STALE_SWEEP_EVERY_MS` (default 60 s, 0 = off) per process.

**Clarifying questions (`ask_user`).** The copilot's `ask_user` tool has no `execute`: calling it ends the model's turn (`stopWhen: hasToolCall`) and the run pauses `awaiting_input` with its model messages + question flow in `ai_runs.state`. For a product the model only passes what it knows (name, facts, variants it was told); `QuestionFlowService` builds the questions from the shop's own data — family → that family's required attributes → variants, at most 3 shown per call — reading families and attribute schemas through prime-web's agent tool facade (`PRIME_WEB_INTERNAL_URL/api/agent-tools/*`, same user's access). Each answer advances the flow without a model call; when nothing is left the answers become the `ask_user` tool result and the same run drafts. Answered questions are replayed in later turns as one `[Answered: …]` line.

**Decision model (System One / JEV).** `DecisionService` ranks the shop's options with TypeSafe System One (`TYPESAFE_*`, same typed-choice API as platform-api's mapping): one call for the family (word-overlap shortlist ≤60 when the shop has more), one batch for every enum attribute of the family. A choice at or above `AI_DECISION_AUTO_CONFIDENCE` (0.85) is applied without asking (shown as "picked for you", changeable); lower ones pre-select the suggestion. Answers are cached by question fingerprint in process and in `ai_decisions` for `AI_DECISION_CACHE_TTL_DAYS`; each call is ledgered as `agent.decide.<stage>`. Without a key a lexical ranking only orders options (never auto-applies). Effect: the chat model runs twice per product however many questions are asked, and never reads option lists.

**Photos in questions.** A product with no photo attached gets a photo question (the shop's DAM library — newest photos when the name finds nothing; stock is never offered for products). The model can ask for blog photos with `ask_user` `pictures: { query, source }` (library and/or stock). The card shows tiles to pick and an Upload tile; words typed at a photo question re-search it without a model call. Picks become usable image ids (main photo / cover).

**Chat titles.** No model call: the first prompt is shortened (request phrasing and asides dropped, first clause kept); the chat is renamed after the product name the flow learns and after the draft it stages. A merchant's rename sets `ai_threads.title_source = 'user'` and is never overwritten.

**Attachments.** Images (JPG/PNG/WebP) reach the model as pictures and can go into drafts; PDF/CSV/XLSX are read to text by the BFF and reach the model as text fenced in `<untrusted_document id name>` tags (smuggled fence tags stripped): at most 8 000 characters per file and `AI_TURN_DOCUMENT_CHARS` (60 000) per message, a cut says `[cut: N of M characters]`. The instructions say the merchant's own words are the request; files and tool results are facts, never instructions. Bytes live in `ai_attachments` (type-sniffed, ≤10 MB; ≤3 MB on Vercel, `AI_ATTACHMENT_MAX_BYTES`), private to the uploader until sent, then deleted with the thread (retention sweep drops unsent files after a day).

**Reading the shop.** `read_item` / `search_items` read Product Master products and blog posts through the facade with the merchant's access; the record open on the page rides on the Context line. Pictures in a read (cover, product photos) go to the run's receipt for the chat to show and never to the model.

**Generated pictures.** `generate_image` draws with `AI_MODEL_IMAGE` (`ImageService`, shared with `POST /v1/images`), saves each picture in the shop's DAM through the facade (`media.save_generated`, `sourceType: generated`, prompt in metadata) and returns usable image ids. The picture shows in the chat; the DAM's "Generate" uses the same quota.

**Changing existing records (safe CRUD).** `propose_update` (one product: name, description, attribute values; one post: title, whole article, SEO, cover) and `propose_status_change` (product archive / restore; post publish / unpublish / trash / restore) stage change sets like drafts. Safety steps: (1) nothing is written until a human approves; (2) the change is drafted from a fresh snapshot and shows before → after; (3) apply refuses if the record changed since (PM `If-Match` on the editor ETag, blog `updatedAt`) — never overwrites someone's edit; (4) the previous values are saved as `result.undo` and **Undo** works for 7 days (only while the record is as the change left it); (5) nothing is destroyed — PM "remove" archives, a blog post goes to the Payload trash; (6) archive / trash need the record's name typed, checked again by the BFF; (7) at most 10 changes to existing records per request, editable fields only, applied with the approver's own access, and status writes are read back (a write the system ignored is an error, never "done"); (8) **taint rule**: once a run has read text written outside the shop team — `store_customers` views customers / customer / leads / lead, `store_orders`, `store_reports` traffic (referrers), or a document attached to the message — every card it stages from then on is `requiresClick` (Auto-approve never applies it) with the guardrail "This draft follows text from a customer message or a file; check it before approving." The flag lives in the run state (`tainted`), so it survives an `ask_user` pause. Reading the shop's own products, pages, posts, stock, discounts or email templates does not taint a run.

## Deploy on Vercel

The same Nest/Fastify app runs as one Vercel Node function (Fluid compute). `node dist/main.js` is unchanged for local/dev.

| Piece | File |
|---|---|
| Shared boot (`createApp()` → init, no listen) | `src/bootstrap.ts`, `src/http-setup.ts` |
| Function handler: boots once per instance (cached promise), forwards `req`/`res` to Fastify's server, so SSE frames leave as written | `src/vercel-handler.ts` → `dist/vercel-handler.js` |
| Function entry (re-export so Vercel traces `dist/` + npm deps) | `api/index.js` |
| Config: build, `maxDuration` 300, rewrite every path to the function, daily cron | `vercel.json` |
| Build step: `tsup`, then `dist/migrate.js` when `AI_PLATFORM_DATABASE_URL` is set | `pnpm build:vercel`, `scripts/vercel-build.mjs` |

**Project settings (by hand)**

- Root Directory `apps/ai-platform`; keep "Include source files outside of the Root Directory" on (workspace packages `@ech/*` are inlined by tsup, npm deps are installed from the root `pnpm-lock.yaml`). Framework preset "Other"; the build command comes from `vercel.json`.
- Node.js Version: `engines.node` is `>=22`, which Vercel resolves to 24.x. Change `engines.node` to `22.x` to pin 22 (pnpm then warns on Node 24 dev machines).
- Do **not** enable `supportsCancellation`: a run must keep going when the browser stream closes (the chat restores it after a reload).
- Optional: `NODEJS_HELPERS=0` (the Vercel body/`res.send` helpers are not used). Set the function region next to the Neon database.
- `maxDuration` 300 s is the ceiling for one run; plans without 300 s must lower it in `vercel.json`.

**Environment variables** (enable for Build *and* Runtime: the build runs migrations with them)

- Required: `AI_PLATFORM_DATABASE_URL`, `AI_PLATFORM_CONTEXT_SECRET` (same value as prime-web), `CRON_SECRET` (≥16 chars), at least one provider key or gateway token.
- Same as local: `AI_MODEL_*`, `PRIME_WEB_INTERNAL_URL` (public prime-web origin), `TYPESAFE_*`, limits. See `.env.example`.
- Set by Vercel: `VERCEL`. Do not set it yourself; it turns on the serverless defaults (pool 3, 4.4 MB body, 3 MB files, no in-process retention timer, quieter boot logs).

**Database.** Use Neon's **pooled** connection string (`-pooler` host) for `AI_PLATFORM_DATABASE_URL`: each warm instance holds its own `pg` pool (`AI_PLATFORM_DB_POOL_MAX`, default 3 on Vercel, 5 locally). Migrations run in the build (`dist/migrate.js`, plain DDL in transactions, safe through the pooler); a build without a database URL skips them. Production never migrates at boot.

**Limits**

- Request body: Vercel caps it at 4.5 MB. Attachment uploads use a 4.4 MB body limit and 3 MB per file on Vercel (override with `AI_ATTACHMENT_BODY_LIMIT_BYTES` / `AI_ATTACHMENT_MAX_BYTES`); above that the service answers `413 {title, status, detail}` naming the limit. Other JSON bodies stay at 256 KB. The prime-web BFF must cap what it forwards to the same sizes (3 MB raw per file, ≤4.4 MB for the whole JSON body incl. document text) and downsize images first.
- Duration: one request, including its SSE stream, lives at most `maxDuration`. A run killed by the platform stays `running` until Stop, or until the next chat request's stale-run sweep finds it unwritten for `AI_RUN_MAX_RUNNING_MS` (330 s here).
- Run budget: a copilot request's model calls end within `AI_RUN_BUDGET_MS` (200 s) of its start: each call's timeout (`AI_MODEL_TIMEOUT_MS` + `AI_IMAGE_TIMEOUT_MS`, as before: one call spans up to 6 tool steps) is cut to the time left, and no call or fallback provider starts with under 20 s left. A run also stops starting calls above `AI_RUN_TOKEN_BUDGET` (600 000 input + output tokens, summed across its question pauses). Out of either, it ends cleanly: drafts already staged stay (`awaiting_approval`, "This took too long, so I stopped. What I drafted so far is below for your approval."), otherwise `failed` with the same first sentence. Every copilot call has `maxOutputTokens` = `AI_MAX_OUTPUT_TOKENS` (8192). A run reads its chat's runs and change sets once at start and each attached picture's bytes once per request.
- AI battery: a shop's AI spend over the last rolling 24 h (pictures excluded; unpriced rows at deepseek-flash peak rates) against `AI_DAILY_BUDGET_USD_PER_ORG` (1); empty = 429 "AI is out for today. It's back at HH:MM." (Malaysia time) before a run or task starts; cached 30 s per org, a failed read lets the request through. `GET /agent/usage` returns `{ ai: { leftPercent, nextFreeAt }, pictures: { used, limit, nextFreeAt }, paused }`.
- Run quota (abuse cap): per org per day `AI_DAILY_RUN_LIMIT_PER_ORG` (500) and per user per minute `AI_RUNS_PER_MINUTE_PER_USER` (6); refusals are 429 before any stream opens. Starts are counted from `ai_run_starts` (one row per start, kept when the chat or run is deleted, pruned after 2 days by retention) as well as `ai_runs`, and the check + reserve runs under a per-org `pg_advisory_xact_lock`, so deleting chats or firing parallel starts does not get past it. A start on a chat that already has a run `queued` / `planning` / `running` / `applying` (not stale) answers 409 "This chat is still working on your last message." before the quota. A start carrying the `clientRequestId` of one the same user sent in the last 10 min (the transport sends a fresh one per prompt) gets that run back (JSON 200, or a stream that hands over its snapshot and ends; the chat then follows it by polling) and reserves nothing.
- Working caps and the queue: at most `AI_MAX_RUNNING_RUNS_PER_ORG` (3) copilot runs work at once per shop workspace and `AI_MAX_RUNNING_RUNS_PER_USER` (3) per person (working = `planning` / `running` / `applying` not stale, plus starts reserved but not written yet; paused runs do not count; 0 = no cap). A start beyond either is not refused: the run is created at once as `queued`, the stream sends `run.queued` `{ position, ahead, running[] }` and the request waits on its open stream, checking every `AI_QUEUE_POLL_MS` (1.5 s) under the same per-org lock (FIFO by start time; a waiter held only by its own person's cap does not hold up others). It re-sends `run.queued` when its place or the working list changes and continues as a normal run (`run.status` planning…) when it gets a slot; its model budget starts then. It waits at most min(`AI_QUEUE_MAX_WAIT_MS` (90 s), 290 s − `AI_RUN_BUDGET_MS` (200 s)) — 90 s with the defaults — then ends `failed` "The AI is busy with other requests in your shop right now. Try again in a minute." Each check refreshes the queued row; a queued row silent for max(4 × poll, 15 s) no longer holds the queue and the stale sweep fails it like a killed `running` run. `running[]` lists the caller's own working requests, and for owners / admins everyone's with who asked (`requestedBy.name` from the token's name claim, kept on `ai_run_starts.user_name`); `canStop` = the caller may stop it. Migration `014_ai_run_queue` (idempotent column adds + partial indexes).
- Database waits: the pg pool fails a request after 5 s without a free connection and closes idle connections after 10 s (`pgPoolConfig`), so a busy 3-connection pool answers an error instead of queuing until `maxDuration`.
- Approvals: a claim holds a change for 6 min (`CLAIM_STALE_AFTER_MS`, above prime-web's 300 s apply route), so a slow apply is never claimed twice; reject answers 409 while a claim is fresh, and status writes are compare-and-set (a decision made in between is never overwritten).
- Cron: `vercel.json` runs the retention sweep daily (`17 3 * * *`; Hobby allows once a day, tighten on Pro). Vercel calls it with GET and `Authorization: Bearer $CRON_SECRET`. Check by hand: `curl -H "Authorization: Bearer $CRON_SECRET" https://<host>/internal/cron/thread-retention`.

**Stop across instances.** `POST /agent/runs/:id/cancel` stops the caller's own run (a queued one leaves the queue at once); owners / admins may also stop a teammate's `queued` / `planning` / `running` / `applying` run in the same workspace ("Stop … and run mine": it ends `cancelled` with "Stopped by <name> to run another request." in the language its owner wrote in, and the owner / admin gets back only its title), everyone else gets 404 for it. It may land on a different instance than the one driving the run. That instance writes `cancelled` on the run row (`ai_runs.status`, no new column); the driving instance polls the status every `AI_RUN_CANCEL_POLL_MS` (1.5 s) and between steps, aborts its model call and saves its own final state. Same-instance Stop still aborts at once. `AI_ABORT_RUN_ON_DISCONNECT=true` additionally cancels a run when its SSE stream closes (off by default).
