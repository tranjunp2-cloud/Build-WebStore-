# Destination in prepared master JSON

## Config mode (current contract)

After every selected Store is VERIFIED, append its ledger-verified destination directly into that Store object in the existing prepared master file:

```json
"destination": { "tenantId": 425, "siteId": 424, "productCategories": [] }
```

Keep all original collections/values and Store ordering. Keep one output for each input part at the same prepared path. Unselected Store values remain unchanged; JSON whitespace may change. Exporter originals are never edited. Users-only category mappings are empty because that mode does not import categories. Full mode writes `productCategories` as an array of verified target category IDs (for example, `[98, 99]`). The private destination manifest retains sourceRef/targetId pairs for provenance and validation. No extra master tree or compact destination-map is generated by config mode.

Prepared is sealed as a handoff once finalization starts. Original import/export manifests and encrypted credentials remain unchanged as evidence of what was imported, not as descriptors of the annotated master bytes. `prepared/destination-manifest.json` records original/output hashes and bytes, source/target/batch identity and finalization status. Normal import/prepare rejects a sealed directory with `PREPARED_MASTER_FINALIZED_USE_EXPORTER_SOURCE`. Start new imports from the original exporter artifact.

One temporary part at a time is streamed, fsynced and atomically replaced. A durable journal records the expected output hash before replacement. `--run PATH --export-only` validates the exact ledger/source/target and journal, then finishes or verifies output without business writes. Changed/missing files are blocked. Incomplete selected Stores block annotation entirely, preserving normal full-import resume until all Stores are verified. Dry-run never annotates.

## Legacy users manifest mode

The following contract applies only to users direct `--manifest` usage. Full direct `--manifest` does not automatically publish destination.

`migrate:pw1:users -- --manifest /absolute/import-manifest.json --all` retains its previous annotated-master output: the same root array, all original Stores and collections (including Pages), and a sibling `destination` on each verified selected Store. IDs come from verified target results. Unselected Stores are unchanged. The source and manifests remain byte-for-byte unchanged; the derived master is a handoff output, not a replacement import artifact.

## Legacy CLI and publication

In legacy `--manifest` mode, use `--output-master /absolute/private/master-with-destination.json`; default to `master-with-destination.json` beside the prepared import manifest. Output must be outside Git and must not already exist. Validate output location before DB writes. Existing `--output-file` remains the optional user report, defaults beside the manifest, not in source.

Read source incrementally with strict JSON validation and bounded per-Store buffering. Retain every source field; only add destination. Verify source SHA-256 while reading. Write private temporary output in the destination directory, fsync, publish atomically without overwriting an existing file, and remove temporary files on failure. JSON whitespace may change; values and array order must not.

In legacy mode, exporter 1.10.0 split-master artifacts use the same CLI. The output-master path contains a `pw1-destination-parts-v1` index, with data in `<output-master>.parts/`. Each input master part produces exactly one destination part with the same filename, Store IDs and order, including parts without selected Stores. Never merge or repartition output parts. Input count/byte limits do not cap annotated output bytes. Verify all input hashes, sizes and IDs; publish the index last and remove newly created parts on failure. Keep the index and parts directory together. Legacy master.json input still produces one destination JSON array.

Only publish after all selected Stores verify. Any Store failure returns nonzero; no partial master is published. Committed DB operations are not rolled back by a file-output failure. The current users CLI has no resume flag; recovery of partial writes needs reconciliation and must not be represented as full success. Ledger VERIFIED in this command means foundation scope only, not full business migration.

## Temporary scope and legacy reuse

The foundation loader does not read mapping reports, CSVs, or customer/product reconciliation files. It verifies manifest bindings and hashes for consumed identity inputs and the complete master, then spools only Tenant/User/Site. This is not full business import certification. Required references outside this scope remain errors. Legacy tenant dashboard objects compare against the same default block list rendered by the application, without changing saved preferences. Existing custom settings, user email or other mapped-value changes still block reuse.

## System creator preparation

Resolve the existing PW2 system account by exact email `sso-service@primeweb.app`, never a fixed numeric ID. The operator specifies the approved PW1 actor reference; do not automatically map every external actor to the system account. Generate private binding/evidence files for that actor using the actual target ID and identity hash. Re-prepare a new artifact with this binding and the snapshot credential CSV; never edit an existing manifest/sidecar because credentials authenticate the binding hash. Missing or ambiguous system email must stop preparation.

## Missing credentials (users and full)

For newly created users only, when the credential record or both passwordHash/key_string are absent, generate an unreported random 256-bit password and persist keyString=null. Record passwordResetRequired=true in ledger creation evidence and, in legacy manifest mode, the users report. This is historical import evidence, not a live reset-status field. Existing users are never reset by migration. Partial credentials, unsupported hashes, decryption errors and mismatches remain blocking. Full importer uses the same missing-both fallback; supplied partial or invalid credentials remain blocking. No passwords enter master, reports or logs. Users must set a new password through an existing recovery flow; the authenticated SSO reset endpoint also populates keyString. No reset email is sent during import.

Local verification 2026-09-23: Store 31 applied and published successfully. Source user 64 retained verified credentials; source user 87 created with password hash, keyString=null and passwordResetRequired=true in both ledger and report. Both VERIFIED. Reset/SSO endpoint was inspected but no email or real password-reset request was executed.

User email is lowercased and trimmed in the target projection before unique checks, checksumming, writes and verification, matching Payload authentication behavior. An accepted owner/email contract with enabled `preserveInvalidUserEmails` preserves an invalid source email exactly through the migration-only writer; canonical case/whitespace uniqueness checks still apply. This does not make that address deliverable or bypass application login validation. The master source remains unchanged. Existing batches are not automatically rebound to changed importer code.
