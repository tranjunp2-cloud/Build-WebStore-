# GitHub #1309 Implementation Planning

## Context

Issue #1309 requires Minimal Business Data scoring to follow the current F37 specification. Existing persistence and tenant isolation are largely reusable, but the score engine still follows the obsolete 35-point Business Data model.

## What Happened

Prepared and engineering-reviewed a reduced implementation plan covering the score contract, phone validation behavior, browser persistence, and acceptance verification. Runtime score activation remains an atomic dependency of #1312 so the application cannot temporarily ship an invalid 85-point total.

## Decisions

- Use `Sites.name` as the Local Business Name; do not add a duplicate field.
- Business Data scoring is Name 7, complete address 8, phone 5.
- Remove hours, category, website, and description from the Business Data bucket.
- A complete address must satisfy the agreed structured-address requirements before earning points.
- Invalid phone input must not persist and should restore the previous valid UI value.
- Coordinate the score rewrite atomically with #1312 to preserve a 100-point engine.
- No database migration is required because the implementation reuses existing fields.
- Keep #1309 ownership to eight files and add no standalone score/phone helper modules.
- Update the stale F37 QA TC mapping before writing tests; tests import the real source logic and reference registered TC-IDs.
- #1312 owns runtime score-route activation and full-engine/API assertions; #1309 stays open until integrated staging QC passes.
- Second review found that `playwright.config.ts` only discovers `e2e/`, while repository policy requires new E2E specs under `tests/`; the plan now includes a config update plus a `--list` discovery gate.
- AC3 browser setup must first confirm the prior phone through a successful PATCH and reload because the existing editor parent uses optimistic state without rollback.
- Follow-up decision: Phase 3 is now a provisional pre-integration QC phase and may run before #1312. Runtime score/API/100-point verification is deferred until #1312 begins, when this plan will be updated with concrete integration artifacts.
- Third review hardened E2E data integrity: require a dedicated schema-valid site, snapshot/restore pending header state alongside name/contact/localBusiness, intercept `local_business_data_saved` analytics writes, and await field saves sequentially to avoid optimistic full-group overwrite.

## Impact

The reviewed plan aligns issue #1309 with the current F37 acceptance criteria while avoiding duplicate abstractions and duplicate API tests. Existing site records remain compatible because no schema change is introduced.

### Findings Fix Record

The server phone schema previously sanitized raw markup before validating it. Inputs such as `<b>123</b>` could therefore fail the client predicate but become valid after server-side sanitization. The schema now validates the raw input first and transforms it only after acceptance, restoring one shared client/server contract while preserving normalized output for valid values.

Whitespace-only legacy country values now fall back to `MY` through trim-aware handling. Regression coverage proves the raw-markup rejection and country fallback at unit/component boundaries. Real-browser persistence remains Phase 3 work, and runtime score/API integration remains deferred to #1312.

### Transactional Contact Save Follow-up

A later review found that a syntactically valid phone update was committed optimistically to parent props before its PATCH completed. If that request failed, the failed value could remain in parent state and leak into a later email or address save.

The review then found that email/address still used optimistic full-group writes and the phone guard lived only inside a `SettingsPanel` instance. A compact/desktop remount could therefore admit an overlapping request, and a legacy-invalid phone could block an unrelated email/address save.

All three contact fields now use one shared component lifecycle and send sparse `{ contactInfo: { [field]: value } }` payloads. The editor parent owns the contact mutex, so it survives panel rerenders/remounts, rejects overlap, and commits contact state only after a successful PATCH. A failed phone, email, or address save restores the last server-confirmed field; unrelated settings retain their existing optimistic behavior. Cross-tab/multi-user conflict resolution remains outside this issue's scope.

The final review cycle aligned address normalization with the server, propagated the parent pending flag through all three `SettingsPanel` mounts, required contact updates to be standalone patches, and made mutex release owner-safe even when fetch setup throws synchronously. A hard client timeout was deliberately not added: aborting an in-flight mutation can hide a later server commit, so timeout remains an unknown-outcome reconciliation concern rather than a safe rollback signal.

Browser E2E verification remains pending in Phase 3. The #1312 runtime scoring dependency and deferred 100-point integration scope are unchanged.

### Latest Review Fix Record

The latest review identified two root causes. Email blur validated and submitted the unsanitized value, while the server stored a sanitized value, allowing the editor state and database value to diverge. Separately, compact-layout test fixtures omitted the new required `isContactSavePending` prop; because unit tests are excluded from the application `tsconfig`, typecheck could not expose that stale contract or prove pending-state propagation.

The focused red run produced 2 expected failures with 35 tests already passing. Email is now sanitized before validation and save, so the client submits and retains the same canonical value as the server. Compact fixtures now provide the required pending prop, and a mock-harness regression verifies that compact layout forwards parent pending-state changes across rerenders.

Fresh green evidence:

- TypeScript typecheck passed.
- Lint passed with warnings only and no errors.
- Production build passed.
- `git diff --check` passed.

Phase 3 real-browser PATCH/reload persistence coverage remains deliberately deferred; this fix cycle does not change the earlier #1312 integration decision.
