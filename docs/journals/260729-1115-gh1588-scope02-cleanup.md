# GH-1588 Scope 02 cleanup

## Context

The branch had accumulated manual-category UI changes, subscription propagation,
migration-helper work, and broad category-delete changes outside literal Scope 02.
Cleanup removed those concerns. Live E2E then exposed a durability/concurrency edge
directly affecting Scope 02, so the final diff retains only the minimum delete
serialization and bounded AI category lock required for authoritative persistence.

## What changed

- Restored the manual Product save path and shared `CategorySelect` behavior.
- Removed unrelated category-delete/concurrency work, then retained only the two-statement
  delete serialization required to coordinate with AI Product relationship inserts.
- Kept tenant-scoped active category loading for the AI parser and review drawer.
- Canonicalized model category output to one allowed `categoryId` or `null`.
- Required one category per AI draft and removed category auto-creation.
- Revalidated selected IDs before side effects and at the AI-only persistence boundary;
  invalid selections return a serializable `CATEGORY_INVALID` result.
- Rejected oversized raw ID lists before parsing, then canonicalized and deduplicated
  IDs inside the bounded list; malformed IDs fail before any Payload lookup.
- Blocked parsing when the tenant has zero active categories and added a localized
  Category-management action without clearing the prompt.
- Kept the review modal mounted during partial-save product refreshes so unsaved
  drafts survive, and protected newer prompt text from an older session's completion.
- Kept background refresh failures non-fatal and ignored out-of-order stale product responses.
- Reworked the permanent browser fixture to create, inspect and clean category/product
  data through the dashboard UI and tenant-scoped Server Actions, with no direct
  collection REST calls or hardcoded IDs.
- Extended guarded `ensure-test-user` provisioning to idempotently ensure the one Site
  prerequisite required by category/product flows on a fresh CI tenant.
- Forced AI-created products to `draft` with `aiReviewPending: true`.
- Added focused unit/API coverage and one Playwright browser-flow scenario.

## E2E rollback and concurrency follow-up

- Initial live E2E exposed Product creates that appeared successful but were not visible to a
  fresh dashboard read. Product creation remains auto-committed and is verified through `findByID`
  before success is reported.
- A shared per-Payload-pool FIFO mutation gate serializes local AI-save and category-delete
  critical sections, so they cannot consume the connections each other needs.
- The AI action holds the active tenant category with `FOR KEY SHARE` on a dedicated Pool client
  while the verified Product write commits. Across instances, category deletion's conflicting
  `FOR UPDATE` lock preserves the same ordering without relying on the process-local gate.
- Both lock paths use a two-second PostgreSQL `lock_timeout`; contention rolls back/releases the
  waiting connection and returns a retryable error instead of allowing cross-instance waiters to
  exhaust database capacity.
- A retryable failure in a mixed AI batch keeps every unsaved draft in the drawer, removes only
  committed drafts, and triggers the partial-success refresh without closing the review session.
- Category deletion acquires conflicting `FOR UPDATE` in one statement, then counts/re-parents/
  deletes in a second statement with a fresh `READ COMMITTED` snapshot. Either delete commits first
  and AI finds no active row, or Product commits first and delete sees its relationship.
- The authenticated user, resolved tenant, and Payload instance are reused inside the dependent
  Product save, so tenant context cannot drift between category validation and persistence.

## Mixed-batch failure follow-up

- Mixed AI batches previously closed the review drawer when one sibling saved successfully
  and another ended with a generic thrown error or a response without an ID.
- Save tracking now uses a generic terminal `hasSaveFailure` state, while intermediate
  SKU-conflict retries are not treated as failures.
- Successful drafts are removed after partial success; every unsaved draft remains available
  for retry.
- TC29 now covers a generic thrown failure, and TC112 covers the no-ID mixed-batch case.

## Decisions

- Scope 02 is isolated to AI-created products; manual product creation remains unchanged.
- Client preflight improves UX, while `saveAiProductAction` is the authoritative
  tenant/active/exactly-one-category boundary.
- Product-list refreshes after partial success are background state updates and must
  not replace the active review session; failures remain non-fatal and only the latest
  response may update product/category state.
- CI provisioning owns only the idempotent Site prerequisite; the permanent E2E owns
  all category/product fixture lifecycle through user-visible flows.
- Prompt cleanup is session-aware: completing prompt A may clear A, but never a newer
  prompt B typed while A was pending.
- Concurrency ownership is explicit: the shared local mutation gate prevents pool cycles, AI holds
  `FOR KEY SHARE` through the verified Product write, and deletion owns the conflicting
  `FOR UPDATE` lock plus a fresh count snapshot; bounded waits protect cross-instance capacity.
