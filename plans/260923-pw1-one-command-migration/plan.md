# PW1 migration — one-command local workflow

Status: implemented; reviewed against current code on 2026-09-24. Related requirement: importer issue #1886. This document describes the current contract; compact destination output is no longer the default.

## Delivered scope

- `migrate:pw1:users -- --config PATH SELECTOR`: temporary Tenant/User/Site migration.
- `migrate:pw1:import -- --config PATH SELECTOR`: supported full business migration; users need not run first.
- Exactly one selector: `--all`, `--store ID`, `--stores ID,ID`, or `--from-store ID --to-store ID`. Full groups default to 100, configurable from 1 to 100. Users processes one Store at a time.
- Strict version-1 config; paths inside config resolve relative to its directory. CLI config/run paths resolve from cwd. Choose exactly one of approved `systemCreator` or existing `creatorBindings` with its evidence dependencies.
- System creator resolves by email `sso-service@primeweb.app`; the source actor is explicitly approved, never a universal default or fixed PW2 ID.
- Config contains paths/options only. Secrets remain in the existing environment loader; credential CSV stays outside Git. Users and full support absent credentials through the same password-reset fallback; partial/invalid credentials still block.
- Local Linux with `flock`, existing DB schema and system user. No automatic schema installation/reset. Vercel execution is outside this delivery.

See [operator README](../../docs/migration/README.md) for complete commands and config.

## Execution and storage

1. Validate CLI/config, local target and existing schema; create a private timestamp/UUID run directory.
2. Acquire the run lock, persist a preallocated batch UUID, prepare approved creator binding and copy/validate the exporter artifact once into `prepared`.
3. Call the existing users/full runner. A typed post-commit callback records the exact ledger batch before business writes. Existing DB leases, entity claims, checksums and per-group checks remain authoritative.
4. After every selected Store is VERIFIED, derive destination IDs from verified ledger claims and validate live target relationships.
5. Finalize existing prepared masters in place, preserving their filenames, Store boundaries/order and all collection values; add a sibling `destination` only to selected Stores. Exporter originals are untouched.

Run layout:

```text
runs/RUN_ID/
├── run.json                       # orchestration state, safe error code
├── events.ndjson                  # workflow phase events
├── binding/                       # only when generated by this run
├── logs/                          # full runner diagnostics
└── prepared/
    ├── import-manifest.json        # original import provenance
    ├── master-manifest.json        # original exporter provenance
    ├── master-*.json               # or legacy master.json; annotated after success
    ├── destination-manifest.json   # finalization journal and output hashes
    └── ...                        # original sidecars/credentials
```

Config mode does not publish `destination-map.json`, another master tree or the legacy personal users report. Prepare still creates one copy of the exporter artifact. Finalization requires temporary disk space for one part at a time, with a conservative disk reserve. JSON whitespace may change, including in unselected parts; data values remain intact.

States: CREATED → BOUND → PREPARED → IMPORTING → IMPORTED → FINALIZING → COMPLETED. Dry-run ends in DRY_RUN_PASSED, may write private preparation/log files, but does not write business/ledger data or annotate masters. Apply after dry-run uses a new run.

## Destination integrity and recovery

`destination` contains tenantId, siteId and productCategories. Foundation categories are empty; full categories are verified sourceRef/targetId pairs. Partial selection is supported; incomplete execution of that selection blocks all annotation with WORKFLOW_DESTINATION_INCOMPLETE.

Before replacing any master, persist `prepared/destination-manifest.json` with original/output hashes, mapping provenance and per-file state. Stream one Store at a time into a private temporary part, fsync, persist the output hash, atomically replace the part and record completion. Recovery checks journal-bound hashes, detects missing/changed files and handles interruption before or after replacement. Repeated completed finalization verifies output without rewriting masters.

Prepared is sealed once the journal exists. Original import/export manifests and encrypted credentials stay unchanged as historical import evidence; they no longer describe the annotated master bytes. The destination manifest describes final output. Normal preparation/import rejects sealed prepared input with PREPARED_MASTER_FINALIZED_USE_EXPORTER_SOURCE. New imports start from the exporter original.

- Full `--run PATH --continue` resumes the exact original batch before finalization; source, target, schema, writer and key guards still apply. It cannot skip unresolved Stores.
- `--run PATH --export-only` works for either scope after all selected Stores verify. It reads ledger/target and finishes or verifies files without business writes.
- FINALIZING/COMPLETED or an existing journal always routes continuation to output verification, never the business runner.
- Users has no DB resume once its batch exists. Partial users writes require reconciliation; export-only cannot complete an incomplete selection.
- Missing batch after recorded progress blocks. Incomplete binding/prepare requires a new run. No automatic partial-setup repair or cross-run cache.
- Target hash identifies host/port/database/schema, not DB incarnation. Keep code/artifact/keys/DB stable for resume. Cross-scope users-to-full reuse is not guaranteed.

Legacy direct `--manifest` commands remain supported. Users legacy output is a separate annotated master (multipart index plus one output per input part); it does not use config-mode in-place finalization. See [destination contract](../../docs/migration/pw1-users-destination.md).
