## CRITICAL

### C1. Stripe orders have no `magicLinkSecret` → email "Pay Now" link is unauthenticated dead-end
`src/app/api/orders/stripe-checkout/route.ts:219-251` creates the order WITHOUT
`magicLinkSecret` (only `checkout/route.ts:225` sets it, and only for `bank_transfer`).

Consequences across the new flow:
- `payment-failed.ts:140` `if (full.magicLinkSecret)` is always false for Stripe orders →
  the retry email CTA is `…/orders/{orderNumber}` with **no `?token=`**.
- `retry-payment/route.ts:80` magic-link branch requires `order.magicLinkSecret`; it is
  null, so the token path can never authenticate. Only the HttpOnly `ct_` cookie works.
- Net effect: a buyer who opens the retry email **on a different device/browser** (the
  whole point of an email magic-link) lands on the public order page, taps "Pay Now",
  and gets **401 Not authorized** from retry-payment. The feature's primary recovery path
  is broken for the most common scenario (paid on phone, email opened on desktop, or
  cookie cleared).

Evidence the cookie is the only working credential: cookie is set in stripe-checkout:309
and retry-payment:229 with `path:'/'`, but it lives only in the original browser.

Fix (pick one):
- Generate `magicLinkSecret = randomBytes(32).toString('hex')` for Stripe orders too in
  `stripe-checkout/route.ts` (and add it to retry-payment's update if missing), so the
  email token path works. This is the intended design — `verifyOrderToken` keys on the
  per-order secret, so a secret is mandatory for any magic-link auth.
- Confirm migration/schema already supports the column (it does — Orders.ts:270).

This is the headline defect: without it, "resume payment via email" does not function
cross-device, which is the user story.

## IMPORTANT

### I1. retry-payment will convert a Bank-Transfer order into a Stripe session
`retry-payment/route.ts:96-101`: `isRetryable` is true when `order.status === 'pending'`
**regardless of paymentMethod**. A fresh BT order is `status='pending'`,
`paymentStatus='awaiting_payment'` (checkout/route.ts:242-244) — so it matches twice.
The handler then builds a Stripe Checkout Session, overwrites `stripeSessionId`, and (via
the awaiting_payment branch NOT triggering, since status stays pending) refreshes
`paymentExpiresAt`. A buyer holding the `ct_` cookie could POST retry-payment on a BT
order and switch it to card/FPX, bypassing the seller's BT reconciliation flow.

UI does not expose this (both call-sites gate on Stripe method), but the API is the trust
boundary and must self-guard.

Fix: add an explicit method gate at the top of the status check:
```ts
const isStripeMethod = order.paymentMethod === 'card' || order.paymentMethod === 'fpx'
if (!isStripeMethod) return 409 NOT_RETRYABLE
```
(or require `RETRYABLE_PAYMENT_STATUSES.has(order.paymentStatus)` AND drop the bare
`order.status === 'pending'` disjunct — that disjunct is what opens the hole).

### I2. retry-payment charges new prices against stale tax/total → price-integrity drift
`retry-payment/route.ts:163-182,207-224`: `buildOrderItems` recomputes `checkoutItems`
from **current** product/variant prices, but the new Stripe session appends
`order.shippingFee` and `order.tax` captured at the *original* checkout, and the handler
**never updates** `order.total/subtotal/tax`. If a product price changed between the
original order and the retry:
- Stripe charges (new line-item prices) + (old tax) + (old shipping).
- `order.total` shown on the confirm/tracking page and in `checkout.session.completed`
  reconciliation still reflects the OLD amount.
This produces a charged amount that disagrees with the persisted order total, and tax that
no longer corresponds to the (changed) subtotal. Reconciliation/refunds will be wrong.

Fix: recompute subtotal from `built`, recompute tax = round(subtotal*0.06), recompute
total, and persist them in `updateData`. Charge and stored total must come from the same
computation. (`built.subtotal` is already returned but discarded.)

### I3. cancel-payment allows `status='new'` — race can cancel a just-paid Stripe order
`cancel-payment/route.ts:60`: CAS WHERE includes `status::text IN (… 'new' …)`. Per
Orders.ts:11,182 `status='new'` is the **Stripe-payment-success target**
(checkout-completed.ts:101 sets `status='new', payment_status='paid'` atomically).

The only thing stopping a paid order from being cancelled is the
`payment_status NOT IN ('paid', …)` clause. Because the success transition is a single
atomic UPDATE, there is no `new`+non-paid window in normal flow — but:
- Including `'new'` is unnecessary and a latent footgun; no legitimate cancellable order is
  ever in `status='new'`.
- API-level race: a direct cancel-payment POST landing in the sub-ms window where the
  webhook UPDATE has committed `status='pending'→'new'/'paid'`… (covered by payment_status
  guard) — safe. But if any future code ever sets `status='new'` before `paid`, cancel
  silently voids a captured payment. The UI does not expose cancel during "verifying", so
  reachability today is low, hence Important not Critical.

Fix: drop `'new'` from the cancel CAS WHERE set — cancellable states are
`('pending','payment_failed')` only. Keeps the payment_status guard as defense-in-depth.

## MINOR

### M1. Concurrent retry creates orphan Stripe sessions (no CAS on retry)
`retry-payment` reads status (non-atomic), then creates a session and updates. Two
concurrent/duplicate POSTs both pass the guard, both create sessions, last `update` wins on
`stripeSessionId`. The losing session stays open until Stripe expiry. Client `setRetrying`
mitigates double-click but not multi-tab. Low impact (webhook matches by session/metadata),
but consider a CAS-style guarded update of `stripeSessionId` or a short re-check.

### M2. payment-expiry cron: TOCTOU between find() and CAS
`payment-expiry.ts:7-20` filters `paymentExpiresAt < now`, but the CAS at :29-38 does NOT
re-check `paymentExpiresAt`. If a buyer calls retry-payment (which sets
`paymentExpiresAt = now+24h`) between the cron's find() and its per-row UPDATE, the cron
still cancels the freshly-extended order. Window is bounded by batch iteration time.
Fix: add `AND payment_expires_at < ${now}` to the CAS WHERE for symmetry.

### M3. retry-payment status guard lists `order.status === 'payment_failed'` but that's a
status enum value present (Orders.ts:191) — OK. However the TERMINAL_STATUSES set includes
`'new'` (correct) yet the `isRetryable` disjunct `order.status === 'payment_failed'` is
redundant with the RETRYABLE_PAYMENT_STATUSES path in practice. Not a bug; simplify for
readability only.

## FOCUS-AREA VERDICTS

1. **Auth / IDOR (cancel & retry):** Sound model. `verifyConfirmToken` is constant-time
   (timingSafeEqual, length-checked) and order-bound (orderId+orderNumber). Magic-link
   `verifyOrderToken` binds via the per-order `magicLinkSecret`, so a token for order A
   cannot authorize order B (different secret) — no cross-order IDOR. BUT see C1: for Stripe
   orders the secret is null so the token path is non-functional (cookie-only). No bypass
   found; the gap is missing auth capability, not excess.

2. **Race conditions:** cancel CAS and webhook-success CAS are mutually exclusive atomic
   UPDATEs — DB-safe (no lost-update, no double-cancel). cancel vs approve-payment CAS also
   mutually exclusive. Remaining concerns: I3 (`'new'` in cancel set) and M1/M2 (TOCTOU).
   Double-click on cancel/retry guarded client-side.

3. **Status guards:** retry TERMINAL_STATUSES correctly excludes cancelled/refunded/
   completed/shipped/new and `paymentStatus==='paid'` — a paid/shipped/cancelled order
   cannot be retried. Defect is the opposite direction: too permissive on `status==='pending'`
   for non-Stripe methods (I1).

4. **Stock:** Verified correct. BT decrements only in approve-payment.ts:117 (seller
   action); Stripe decrements in checkout-completed.ts on capture. Awaiting/pending_verification
   orders never reserved stock, so cancel doing no restock is correct. Reasoning holds.

5. **payment-expiry cron broadening:** SQL guard `payment_status IN (awaiting_payment,
   pending_verification, payment_failed, failed) AND status IN (pending,new,payment_failed)`
   cannot touch a paid Stripe order (status='new' but payment_status='paid' → excluded by
   the payment_status set). In-flight unpaid orders are only cancelled once truly past
   paymentExpiresAt (matches Stripe session 24h expiry). Safe, modulo M2 TOCTOU.

6. **pageshow / sessionStorage back-redirect:** Clean. Flag is namespaced (`pw_stripe_pending`),
   removed-on-read in both the inline script and the React effect, and cleared on the confirm
   page mount (ConfirmClient:164-166). A later fresh checkout cannot inherit a stale flag
   (removeItem precedes parse). The `!isPaid` guard prevents a stale `cancelled=1` from
   showing "failed" on an already-paid order. No false-redirect path found.

7. **Inline script (page.tsx):** Values are read from sessionStorage JSON that the app itself
   wrote (orderId from server response, slug from route), and are passed through
   `encodeURIComponent` before interpolation into `location.replace`. JSON.parse is
   try/caught. No attacker-controlled sink into the script body; no XSS. Acceptable.

8. **payment-retry email token:** `signOrderToken` usage is correct (HS256, per-order secret,
   scope, 24h exp). Token in URL query is the documented magic-link pattern (same as existing
   BT upload links). Standard referrer/log-leak caveat applies but is pre-existing and
   accepted for this pattern. NOTE: token is never actually emitted for Stripe orders (C1).

9. **SSE in ConfirmClient:** Cleanup correct (`return () => es.close()`, errorCount cap at 5,
   stream self-closes on terminal). `clearCart` is idempotent-guarded by `clearedRef`
   (lines 89,202-206) so no double-fire across SSE message + checkout-path clear. SSE
   correctly skipped when `cancelled` (won't become paid via abandoned session). The
   "verifying" state has no timeout, but the stream sends terminal on failure/cancel and the
   server caps at 50s with auto-reconnect — acceptable, not infinite.
